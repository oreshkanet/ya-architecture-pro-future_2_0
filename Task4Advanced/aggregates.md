# Агрегаты доменов

## 1. Patient Management (Управление пациентами)

### 1.1. Patient (Пациент)

| Элемент | Описание |
|--------|----------|
| **Граница** | Один агрегат — один пациент. В состав входят: идентификация, контактные данные, связь с внешними идентификаторами (например, клиент банка), список привязок к учреждениям. Запись на приём (Appointment) - отдельный агрегат. |
| **Инварианты** | Идентификатор пациента уникален в рамках контекста. Один и тот же пациент не регистрируется повторно с тем же набором ключевых атрибутов. Контактные данные и данные, необходимые для регуляторики, заполнены в соответствии с политикой. |
| **Ключ (Root)** | `patientId` (UUID или доменный идентификатор). Используется в событиях домена. |

### 1.2. Appointment (Запись на приём)

| Элемент | Описание |
|--------|----------|
| **Граница** | Один агрегат — одна запись на приём. Ссылается на Patient (id), на ресурс/врача и временной слот. Отмена и перенос — операции над этим агрегатом. |
| **Инварианты** | В один слот не назначается два приёма для одного и того же ресурса. Время приёма в допустимых границах работы клиники. При создании/изменении/отмене агрегат переходит в соответствующее состояние и публикует событие домена. |
| **Ключ (Root)** | `appointmentId`. В событиях также передаются `patientId`, `resourceId`, `scheduledAt`. |

## 2. Clinical Operations (Клинические операции)

### 2.1. Visit (Визит / приём)

| Элемент | Описание |
|--------|----------|
| **Граница** | Один визит — один приём пациента в клинике. Факт приёма, связь с назначениями, персоналом, ресурсами. |
| **Инварианты** | Визит привязан к существующему пациенту и к ресурсу/врачу. Завершённый визит имеет дату/время завершения. При изменении состояния инициирует публикацию событий домена. |
| **Ключ (Root)** | `visitId`. В событиях: `visitId`, `patientId`, `completedAt`, идентификатор подразделения (для аналитики). |

### 2.2. Resource (Ресурс: врач, кабинет, оборудование)

| Элемент | Описание |
|--------|----------|
| **Граница** | Ресурс, доступный для бронирования. Агрегат управляет расписанием и занятостью слотов. |
| **Инварианты** | Двойное бронирование одного ресурса на один слот невозможно. Публикуется события домена при изменении состояния бронирования. |
| **Ключ (Root)** | `resourceId`. |

## 3. Accounts & Credits (Счета и кредиты)

### 3.1. Account (Счёт)

| Элемент | Описание |
|--------|----------|
| **Граница** | Один счёт клиента. Баланс, валюта, статус, привязка к владельцу (клиент/пациент). Операции по счёту могут обрабатываться в контексте Payments. |
| **Инварианты** | Баланс не уходит в отрицательное значение без разрешённого овердрафта. Счёт в статусе "закрыт" не принимает новые операции. |
| **Ключ (Root)** | `accountId`. В событиях: `accountId`, `customerId` (привязка к пациенту/клиенту), `openedAt`. |

### 3.2. CreditContract (Кредитный договор)

| Элемент | Описание |
|--------|----------|
| **Граница** | Один кредитный договор: сумма, срок, график, статус (активен/погашен/просрочен). Связь с плательщиком и счётом. |
| **Инварианты** | Сумма и срок в допустимых пределах продукта. При создании подписанного договора и изменении его состояния публикуются события домена. Изменение статуса при погашении/просрочке согласовано с платежами. |
| **Ключ (Root)** | `creditContractId`. В событиях: `creditContractId`, `customerId`, `amount`, `currency`, `signedAt`. |

---

## 4. Payments (Платежи)

### 4.1. Payment (Платёж)

| Элемент | Описание |
|--------|----------|
| **Граница** | Одна платёжная операция: сумма, счёт/договор, дата, статус (успех/ошибка). |
| **Инварианты** | После перехода в статус "проведён" платёж неизменяем. При успехе/ошибке публикуются события домена. |
| **Ключ (Root)** | `paymentId`. В событиях: `paymentId`, `accountId` или `creditContractId`, `amount`, `occurredAt`, `status`. |

## 5. AI & Research (ИИ и исследования)

### 5.1. ResearchJob (Задача исследования)

| Элемент | Описание |
|--------|----------|
| **Граница** | Одна задача на проведение исследования/обработку ИИ: входные данные (ссылки на визит, снимки и т.д.), тип исследования, статус. Результаты хранятся в этом контексте; в события наружу отдаются только факт завершения и идентификаторы (без ПДн в витрину). |
| **Инварианты** | Задача в статусе "завершена" публикует StudyCompleted. Результат доступен только авторизованным системам (клиника), в аналитику уходят только агрегаты. |
| **Ключ (Root)** | `researchJobId`. В событиях: `researchJobId`, `visitId` (при необходимости), `completedAt`, тип результата (без персональных данных). |

### 5.2. AIResult (Результат ИИ)

| Элемент | Описание |
|--------|----------|
| **Граница** | Результат работы ИИ по конкретной задаче. Владелец — контекст AI & Research; потребители — клинические системы. Для витрины публикуется только факт "результат готов" и метаданные (тип, время), без диагнозов и персональных данных. |
| **Инварианты** | Связан с ResearchJob. Публикуется AIResultReady после сохранения результата. |
| **Ключ (Root)** | `resultId` или связка `researchJobId` + версия. |

## 6. Data Mart (Витрина данных)

### 6.1. DataSlice / ReportDefinition (срезы и отчёты)

| Элемент | Описание |
|--------|----------|
| **Граница** | Агрегаты витрины строятся по подписке на события; не владеют первичными данными. Срез или определение отчёта — это сохранённый запрос/агрегат по событиям (количество регистраций, объём платежей, метрики по исследованиям и т.д.). |
| **Инварианты** | Данные в витрине не содержат медицинских карт и персональных медицинских результатов; только агрегаты и идентификаторы в соответствии с политикой доступа. Обновление — идемпотентное по event id. |
| **Ключ (Root)** | `sliceId` / `reportId`. Для проекций по событиям — композитный ключ по типу сущности и id события (дедупликация). |
