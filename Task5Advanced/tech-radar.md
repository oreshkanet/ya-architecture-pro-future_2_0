# Расширенный технический радар «Компания 2.0»

Технологический ландшафт и архитектурные паттерны с учётом целевой трансформации (горизонт 3 года). Статусы:

- **Adopt** — рекомендуем к активному использованию.
- **Trial** — опробовать в проектах с пониманием рисков.
- **Assess** — оценить пригодность для компании.
- **Hold** — не расширять использование; планировать вывод.

---

## 1. Архитектурные паттерны

| Паттерн | Описание | Статус | Комментарий |
|---------|----------|--------|-------------|
| **Event-Driven Architecture** | Взаимодействие доменов через события, шина событий, реактивные потоки | **Adopt** | Целевая модель интеграции; пилот в 1–2 доменах, далее масштабирование. |
| **Data Mesh** | Данные как продукт по доменам, владение данными у бизнес-доменов, единая инфраструктура самообслуживания | **Trial** | Внедрение через пилот (финансы, пациентский поток); роли Data Product Owner, Data Engineer. |
| **Self-Service BI / витрина данных** | Портал самообслуживания: срезы, конструктор отчётов, доступ по ролям без централизованной разработки каждого отчёта | **Adopt** | Реализация прямой цели - витрины данных; строится поверх доменных данных и событий. |
| **Bounded Context (DDD)** | Чёткие границы доменов, контракты на границах, независимость контекстов | **Adopt** | Основа разбиения на Patient Management, Fintech, AI, Clinical Operations, Data Mart. |
| **Anti-Corruption Layer** | Слой адаптации между легаси (DWH, Camel) и целевой событийной моделью | **Adopt** | Временный паттерн на этапе миграции; снижает связность с legacy. |
| **Centralized Data Warehouse (монолит DWH)** | Единое хранилище и ETL для всех данных и отчётности | **Hold** | Текущее состояние; не расширять; поэтапный вывод, замена доменными хранилищами и витринами. |
| **Point-to-point интеграции через ESB** | Синхронные и пакетные интеграции через единую шину (Camel) | **Hold** | Использовать только как мост совместимости; целевая интеграция — события. |

## 2. Платформы и инфраструктура

| Технология | Категория | Статус | Комментарий |
|------------|-----------|--------|-------------|
| **Облако (Yandex Cloud / мульти-облако)** | Инфраструктура | **Adopt** | Целевая платформа; отдельные среды по доменам, масштабирование, отказоустойчивость. |
| **Kafka-совместимая шина событий** (Kafka, Yandex Message Queue, и т.п.) | Messaging | **Adopt** | Основа ESB: топики, очереди, DLQ, каталог схем. |
| **Object Storage (S3-совместимый)** | Хранение | **Adopt** | Данные озёр, бэкапы, state Terraform, артефакты. |
| **Kubernetes / managed K8s** | Оркестрация | **Trial** | Для доменных сервисов и потоковой обработки; пилот в выбранных доменах. |
| **Terraform / IaC** | Инфраструктура | **Adopt** | Унификация окружений, CI/CD, удалённый state. |
| **On-premise SQL Server (DWH 2008)** | Хранение / БД | **Hold** | Легаси; миграция в облачные хранилища и доменные БД; не развивать. |
| **Apache Camel (ESB)** | Интеграция | **Hold** | Только мост на время миграции; целевая интеграция — события. |

## 3. Данные и аналитика

| Технология | Категория | Статус | Комментарий |
|------------|-----------|--------|-------------|
| **Потоковая обработка** (Kafka Streams, Flink, облачные сервисы) | Обработка данных | **Trial** | Потоковые витрины, near real-time; пилот в 1–2 доменах. |
| **Доменные хранилища и витрины** (облачные БД, колоночные хранилища) | Хранение / аналитика | **Adopt** | Данные во владении домена; витрина данных потребляет через события и API. |
| **Superset** | BI / визуализация | **Trial** | Возможный фронт для витрины данных или часть Self-Service; оценить вместе с альтернативами под портал. |
| **Schema Registry / каталог схем событий** | Управление данными | **Adopt** | Версионирование контрактов событий, совместимость доменов. |
| **Кастомная тяжёлая логика в DWH и ETL** | Аналитика | **Hold** | Перенос в доменные сервисы и потоковые витрины; не наращивать в DWH. |
